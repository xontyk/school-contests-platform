# Платформа школьных конкурсов

Прототип веб-платформы для хакатона (возрастная группа **9–11 классы**).
Позволяет школе анонсировать конкурсы, вести учёт участия школьников,
формировать и выдавать дипломы. Полностью клиентское решение —
сервер не требуется, все данные хранятся в `localStorage` браузера.

## Запуск

Бэкенд не нужен. Открыть `index.html` в браузере (двойной клик,
либо `File → Open`). При первом запуске автоматически создаются
тестовые данные: 4 конкурса, 5 учеников, 2 администратора.

Для демонстрации импорта участников используется файл
[`assets/sample-participants.csv`](assets/sample-participants.csv).

## Архитектура и «API-слой»

Код разделён на три независимых слоя, чтобы при подключении
реального бэкенда менялся только нижний слой:

1. **`db.js`** — хранилище. Знает только про `localStorage` и формат
   коллекций (`users`, `contests`, `participations`, `diplomas`,
   `diplomaTemplates`). Содержит generic CRUD (`getAll/getById/insert/
   update/remove`) и генерацию тестовых данных.
2. **`api.js`** — бизнес-логика и контракт API. Экспортирует объект
   `api` с разделами `api.auth`, `api.users`, `api.contests`,
   `api.participations`, `api.diplomas`, `api.reports`. Все методы —
   `async`/`Promise` и имитируют сетевую задержку (`setTimeout`),
   как у настоящего REST-клиента. Здесь же живёт валидация
   (например, «ученик не может подать заявку дважды на один конкурс»).
3. **Страницы (`student.js`, `admin.js`, `login.js`)** — работают
   только через `api.*`, ничего не знают про `localStorage` напрямую.

Благодаря этому разделению переход на настоящий бэкенд сводится к
замене реализации методов внутри `api.js` на `fetch('/api/...')` —
сигнатуры (`api.contests.list()`, `api.contests.create(data)` и т.д.)
и весь код страниц останутся без изменений.

## Разграничение ролей

- **Ученик** (`student.html`): видит афишу конкурсов, может подать
  заявку на участие, отслеживает прогресс (система уровней по
  накопленным баллам), скачивает дипломы для завершённых/выигранных
  конкурсов.
- **Администратор** (`admin.html`): управляет конкурсами (CRUD),
  импортирует списки участников (CSV/JSON), формирует и выгружает
  отчёты по активности (CSV).

Доступ к `student.html`/`admin.html` без входа или не с той ролью
автоматически перенаправляет на страницу входа (`requireRole()` в
`common.js`).

## Реализованный функционал

- Проработанная структура данных (5 сущностей, см. схему выше).
- Эмулированный API-слой с CRUD для пользователей, конкурсов, участий
  и дипломов + отдельный модуль отчётов.
- Разграничение ролей ученик/администратор с собственной навигацией.
- Админ-панель: создание/редактирование/удаление конкурсов, импорт
  участников из CSV или JSON, формирование и скачивание CSV-отчёта
  по активности.
- Личный кабинет ученика: афиша конкурсов с подачей заявки, список
  участий со статусами и баллами, система уровней/прогресса,
  скачивание дипломов.
- Дипломы: 2 готовых SVG-шаблона для скачивания «как есть», плюс
  опциональная генерация персонального PNG-диплома с именем ученика
  (рисуется на `<canvas>`, без сторонних библиотек).
- Тестовые данные: 4 конкурса, 5 учеников, 2 администратора,
  10 участий, 6 выданных дипломов.

## Сценарий демонстрации (≈45 секунд)

1. Вход под `petr / 1234` → вкладка «Мой прогресс»: уровень и баллы.
2. «Афиша конкурсов» → подать заявку на новый конкурс.
3. «Мои участия» → скачать диплом за прошлый выигранный конкурс.
4. Выход → вход под `admin / admin123`.
5. Вкладка «Конкурсы» → создать новый конкурс через форму.
6. «Загрузка участников» → выбрать конкурс, загрузить
   `assets/sample-participants.csv`, подтвердить импорт.
7. «Отчёты» → сформировать отчёт по активности и скачать CSV.

## План масштабирования

Текущая архитектура специально рассчитана на лёгкий переход к
боевому бэкенду:

1. **Бэкенд и БД**: заменить `db.js` на HTTP-клиент к REST/GraphQL API;
   данные переносятся в реальную СУБД (PostgreSQL/MongoDB) по той же
   схеме сущностей (`users`, `contests`, `participations`, `diplomas`).
2. **Авторизация**: заменить проверку логина/пароля в `localStorage`
   на серверную аутентификацию (JWT/сессии), хеширование паролей,
   восстановление доступа.
3. **Файлы**: шаблоны и сгенерированные дипломы переносятся в объектное
   хранилище (S3-совместимое), генерация PDF — на сервере
   (например, через headless-рендер HTML в PDF) вместо `<canvas>`.
4. **Роли и права**: расширить модель ролей (например, «куратор
   конкурса», «завуч») и добавить проверку прав на уровне API, а не
   только на уровне интерфейса.
5. **Краевые случаи**, заложенные в архитектуру заранее: уникальность
   участия (`userId + contestId`) уже проверяется в `api.participations.create`;
   при переходе на сервер та же проверка переносится в БД (уникальный
   индекс) и дополняется конфликт-резолюцией для одновременных
   действий нескольких администраторов (например, оптимистичные
   блокировки при подтверждении достижений).
6. **Отчёты**: текущий CSV-экспорт на клиенте заменяется на серверную
   генерацию отчётов (с пагинацией и фильтрами) для больших объёмов
   данных.

## Примечания

- Пароли хранятся в открытом виде в `localStorage` — это сознательное
  упрощение для прототипа без сервера, не предназначено для продакшена.
- Код содержит комментарии к ключевым функциональным блокам
  (см. заголовки файлов `db.js`, `api.js`, `student.js`, `admin.js`,
  `diploma.js`).
